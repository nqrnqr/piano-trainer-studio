## 1. 任务与完成标准

在现有 TypeScript 项目上改进横向乐谱：**自动演奏到反复、返始或下一轮 Loop 时，后续乐句出现在当前乐句右侧，光标和视口继续向右推进。**

例如：

```text
原谱：        |: A B :| C D
实际演奏：    A B A B C D
横向显示：    A → B → A → B → C → D
```

用户需要的是完整反复后的演奏过程。不能通过跳过反复、只限制 scrollLeft、在边界瞬移光标或隐藏光标来达到表面上的单向滚动。

必须保留：

- 多行传统显示、原始 MusicXML/MXL 和曲库存储格式。
- MIDI 输入、音频输出、Wait / Follow / Realtime 的判定与调度规则。
- 正误反馈、提前输入、延音、左右手分配、速度、移调、缩放和布局切换。
- 当前静态启动器、离线资源、TypeScript 严格配置及 vendor 版本。
- `fddd3ac` 的 suspend/resume/dispose 生命周期修复。

范围说明：

- 正常自动演奏中的反复和 Loop 不允许可见回跳。
- 用户主动 Reset、点击跳转、手动拖动滚动条可以改变位置；这属于明确的导航操作。
- 切换布局和缩放可以重新排版，但必须保留当前演奏到哪一遍、当前待弹事件与计分。
- 本方案分阶段覆盖有限反复和无限 Loop。只完成有限反复时，应报告为阶段交付，不能声称整个需求完成。
- LED 是非核心功能；保留可选输出端口，不新增硬件功能。

## 4. 推荐架构

### 4.1 保留原谱作为演奏依据，新增横向显示模型

推荐采用：**原谱及其现有演奏引擎 + 根据演奏顺序生成的横向显示谱 + 双向位置映射**。

```text
原始/当前移调后的谱
  ├─ 原谱 OSMD → 现有练习、MIDI、音频、计时
  │                 └─ 当前正式显示的演奏事件
  └─ 独立遍历 → 演奏顺序 → 显示用 XML → 横向 OSMD/渲染分段
                              ↑             ↓
                         事件与音符映射 ← 显示几何坐标
```

传统模式继续使用原有渲染路径。横向模式使用派生显示谱；显示实例不能再次执行原谱反复，也不能产生音频或判定。

有限反复先用一个独立显示 OSMD 验证正确性；H5 再引入分段渲染，沿用同一显示位置接口。原谱实例可以隐藏，但不能依赖宽高为零的容器计算几何；具体宿主方式在 H1 验证。

不要把展开谱直接塞进现有 `loadScoreIntoApp` 作为当前原谱。这会重置播放和计分，并改变小节编号、NoteRef、Loop、移调与曲库内容。

### 4.2 为每次演奏出现建立独立身份

需要分别表达：原谱位置、某次出现、当前会话中的播放事件、具体显示副本。以下是类型设计草案，实施时按项目类型风格收敛：

```ts
interface SourceEventAddress {
  sourceMeasureIndex: number;       // 数组索引，不是 MusicXML 的展示编号
  timestampWhole: number;
  sourceEventOrdinal: number;      // 同小节、同时间的事件仍须可区分
}

interface PerformedEvent {
  scoreRevision: number;
  runId: number;                   // 新加载、主动 Reset/Seek 开启新的导航会话
  eventId: number;                 // 当前会话内每次正式推进分配，单调递增
  traceStepIndex: number;          // 原谱有限演奏路径中的步号
  measureOccurrenceId: number;     // 某小节此次出现的唯一身份
  loopIteration: number;
  source: SourceEventAddress;
}

interface DisplayNoteAddress {
  eventId: number;
  sourceNoteRef: NoteRef;          // 使用现有领域 NoteRef
  displayMeasureId: string;
  displayNoteId: string;
}
```

规则：

- 单次正常推进才产生新 eventId；重复 update、resize、重绘、切换布局不能被计为新的演奏事件。
- 同一小节反复第二遍、第三遍必须得到不同 occurrence；用户 Loop 轮次也独立编号。
- 不能用“小节号 + MIDI 音高”匹配音符；双声部同音、和弦、跨谱表和装饰音会发生冲突。
- 源音符与副本音符不是同一个 OSMD 对象。映射应基于验证过的结构地址及事件顺序，包含 part/staff/voice/音符序号等必要信息；音高和时值用于校验，不能作为唯一身份。
- `sourceNoteRef` 在布局切换时不失效。派生显示重建使用独立 displayRevision，不应提升原谱 scoreRevision。
- 反馈记录保存来源身份和演奏实例，重绘时重新求锚点，避免只保存旧 SVG 像素坐标。

### 4.3 独立遍历与可靠恢复

以当前 vendor 实际支持的演奏路径为依据，不另写一套与 OSMD 冲突的反复解释器。

- 优先验证能否在同一 Sheet 上创建独立 iterator；查清本地 OSMD 实际接口后，才在 vendor 类型中添加所用字段。
- 若不能可靠隔离，使用单独加载同一内容的规划实例。不能借用正在演奏的 cursor 做 reset/扫描，再仅按小节和时间恢复。
- 当前 `ensurePreviewTimelineBuilt()` 的 notes 会按练习手和键域过滤，不可直接作为完整显示谱的内容来源。显示遍历需要包含所有谱表、休止符和非练习声部。
- 扫描应能区分单小节反复、只有一个和弦的反复，以及同一时间的多个声部事件。不能仅靠小节索引变化或时间戳下降判断新的一遍。
- 保留遍历上限，超限时给出明确错误，不静默输出被截断的“完整”展开谱。
- 点击第二遍及恢复第二遍可以用从起点重放到精确 traceStepIndex 的方式实现；如使用快照，必须验证内部反复状态的复制安全性。先确保正确，再做快照性能优化。
- 播放开始、预览重建和布局切换都不能把当前第二遍恢复成第一遍。若现有共享预览恢复路径会破坏该约束，应以独立用例做必要修复，避免继续沿用错误的恢复方法。

### 4.4 显示用 MusicXML

新增纯转换模块，把原谱 XML 和已确认的演奏顺序转换为派生 XML 及映射表。

必须处理：

1. 多 part 小节同步展开，保留 `backup`、`forward`、和弦、声部、休止、歌词及必要显示指令。
2. 一房/二房等按路径选择；移除派生谱中已消费的 repeat、ending 和导航指令，避免显示实例再次重复。不要误删音乐动态或速度。
3. 回到前面小节时恢复其有效 divisions、谱号、调号、拍号、移调等上下文；这些属性可能只在更早的小节声明。
4. 原编号缺失、重复、非数字、弱起小节均使用结构索引映射，不能把 `number` 当作唯一主键。
5. 跳转和分段处的 tie/slur、延长线、变音记号及有效速度上下文需要专门谱例。维持真实演奏连接，不要一律删除跨边界连线，也不要制造原本不存在的延音。
6. 保留原小节编号的可追溯性；必要时显示“第 2 遍”，不要把内部 chunk/event ID 展示给用户。
7. MXL 使用已有提取/规范化入口，不新增独立 ZIP 或转换依赖。移调后从当前有效谱内容生成显示模型，而不是从未移调的原稿生成。
8. 派生数据仅为内存缓存，不能覆盖曲库 rawData、currentScoreOriginalData 或备份内容。

H1 必须证明原谱与展开谱的事件/音符映射可验证，包括同音多声部和装饰音。若所选复制方法不能保留这些关系，应先调整适配边界；不能降级为模糊音高匹配后继续集成。

### 4.5 正式显示事件与预取事件

目前 playbackLoop 会在等待当前音符完成之前推进 iterator。新显示必须绑定正式展示/待弹的事件。

- 在 coordinator 中为“正式展示当前事件”提供一个明确通知端口；信息至少包含来源地址、traceStepIndex、eventId 和推进原因。
- 原谱 cursor 的内部 update 仍可用于传统显示快照；不要通过统计所有 update 调用次数计算 eventId，因为预览扫描和重绘也会调用它。
- 为首帧、音符推进、休止符推进、反复、Loop、新加载、Reset、Seek、暂停/恢复逐一列出通知时机。
- Wait 未满足当前条件时不能展示下一组；Follow 接受输入后的延迟期间仍保持正确的当前位置。
- 用相同输入序列比较两种布局的 expectedNotes、计分、MIDI/音频输出和调度顺序；显示不得导致重复 note-on 或重复判定。

### 4.6 视口、光标与反馈

新增 `ScorePresentation` 一类窄接口，让 viewport/overlay 消费显示坐标，避免直接依赖单个原谱 cursor DOM。接口可提供：当前光标锚点、音符锚点、小节命中测试、视口宽度/内容长度及重绘通知。

- 普通音符推进与反复边界走同一条滚动路径，不设置“反复时回跳”的特殊分支。
- 保留约 33% 的光标目标区域和自动滚动开关；曲首/曲尾允许自然受边界限制，并保留足够尾部空白。
- Wait 停在当前音符；Follow/Realtime 如需要时间插值，使用现有实际调度窗口，不另建一个随意推算 BPM 的播放时钟，也不能越过尚未正式推进的事件。
- 优先复用当前平滑跟随，只有实测仍有明显台阶时才加入可控插值。不得为了“连续”改变休止符或等待时长。
- 默认动画以真实帧时间计算。尊重 reduced-motion；此设置下可立即定位右侧目标，不要求动画平滑，但不能回到前一份乐句。
- 正确高亮、错误音、延音、debug overlay 都定位到当前副本。第一遍的历史标记不得错误覆盖到第二遍。
- 缩放/切换时保留显示事件身份，并重建其所有必要锚点；不能把旧布局的绝对坐标直接复用。

### 4.7 Loop 与长谱分段

无限 Loop 使用动态显示序列。在当前一轮末尾到达前，准备右侧下一轮，实际播放边界到来时切换 eventId/轮次；保留现有 Loop 范围、计分重置和 count-in 行为。

- count-in 期间下一轮可已显示，但光标不能提前演奏下一轮音符。
- Loop 范围仍按原谱小节表达，UI 的 min/max 不变成展开后小节序号。
- 修改 Loop 范围、移调、重新加载或主动 Seek 时，使过期的预渲染结果失效。
- 按固定演奏片段生成独立渲染块，提前加载前方内容，回收远离视口的旧块；不要每一轮重建整条超长 SVG。
- 统一块间谱表基线、缩放和上下文；禁止每块重复大标题或任意拉伸导致接缝跳动。跨块连线应在视觉上正确衔接。
- 使用稳定的逻辑横坐标和可重设的局部 DOM 原点，避免累计超出浏览器滚动宽度。回收/重设原点时补偿视口偏移，屏幕上的当前音符不移动。
- 不能把“scrollLeft 数值始终增加”作为唯一标准：原点重设允许数值变化，但逻辑位置应前进，视觉不能跳。
- 手动滚动到已回收区域需要按需重建；自动跟随关闭后，不要回收用户正在查看的内容。
- 完成后证明 DOM、OSMD 实例、监听器及历史映射缓存数量不会随 Loop 轮数无界增长。活动事件/按住音符引用的块不能提前释放。

## 6. 分阶段执行

### H0：基线与行为用例

交付：`docs/testing/horizontal-unfolded-baseline.md`。

- 读取当前 git 状态并运行 `npm run check`，记录实际测试数量。
- 保存传统/横向在反复、暂停恢复、布局切换和 Loop 上的当前事件序列。
- 准备小型可读 MusicXML 谱例，每个标明人工预期的小节演奏顺序。
- 核对页面缓存修复仍在；其生命周期测试也属于此次回归。

退出标准：可以稳定复现旧横向模式的反复回跳，基线命令通过，工作区已有修改得到保留。

### H1：验证独立遍历与显示映射

交付：最小独立路径规划、显示 XML 转换原型和真实 OSMD 测试页；尚不替换正式横向模式。

- 验证独立 iterator 或规划实例不会改变原谱当前遍数、待弹音、计分、显示快照。
- 用 `|: A B :| C`、单小节单和弦反复、一房/二房及双声部同音证明展开顺序和音符映射。
- 同时验证多谱表、装饰音、全小节休止和继承调号，不只用四分音符单声部演示。
- 记录实际 vendor 接口、映射算法、当前支持和不支持的跳转类型。

退出标准：第二遍拥有独立的显示坐标，原谱仍按同一事件路径播放；映射完整且无歧义。若技术假设不成立，在此阶段改进方案并记录原因，不带着错误映射进入 H2。

### H2：正式事件身份与精确定位

交付：类型化 PerformedEvent/映射服务，coordinator 的最小通知端口，精确 traceStepIndex 定位。

- 为所有正式推进路径分配事件身份，区分预取和当前展示。
- 重绘/暂停/恢复不增加一次演奏；自动反复和 Loop 正确增加 occurrence。
- 传统显示保持原效果，练习/音频输出序列保持基线。
- 处理共享预览重建及启动恢复不会丢失第二遍状态的问题。

退出标准：受控时钟下三模式推进正确，重复 update 不导致重复事件；第二遍暂停/恢复不会返回第一遍。

### H3：接入有限反复展开

交付：横向布局使用派生谱，传统布局保持原谱，光标/反馈/命中测试使用显示映射。

- 接入加载、布局选择、缩放与移调；准备完成后原子替换显示。
- 给异步任务分配 score/layout generation。用户快速换谱/布局时，旧任务不能覆盖新页面。
- 横向准备过程不阻塞音频调度；提交时用最新正式事件定位，不使用启动准备时的旧位置。
- 原始文件、备份、源 NoteRef 和计分状态保持正确。
- 横向点击第二遍定位到第二遍；切回传统后显示原小节但内部仍保持该遍次，切回横向仍是同一次出现。

退出标准：Wait/Follow/Realtime 在有限反复、一房/二房边界均向右推进，高亮落在正确副本，切换布局不改变接下来应演奏的内容。

### H4：平滑滚动与交互收尾

交付：反复边界使用普通跟随路径，稳定光标区域，历史反馈重投影。

- 验证连续快速音符、长音、Wait 停顿、Follow 提前输入、速度变化及暂停。
- 验证缩放、全屏、窗口宽度变化、自动滚动关闭、手动滚动与 reduced-motion。
- 用真实浏览器前台 rAF 测量轨迹。不能只通过 mock scrollLeft 的单元测试宣布体验完成。

退出标准：前后各一段音符的跟随轨迹在反复边界没有额外回退、瞬移或整屏突变；对任何允许的主动导航明确测试原因。

### H5：Loop 动态追加与分段回收

交付：同一显示模型支持有限长谱和无限 Loop 的分段渲染。

- 提前追加后续轮次，避免到边界才首次渲染。
- count-in、Loop 开关/范围变化和原谱反复组合保持现有实际播放规则。
- 加入块资源上限、旧映射回收、局部原点补偿、手动查看旧块的处理。
- 加载/切换/销毁期间取消待完成任务，并阻止旧回调更新 DOM。

退出标准：至少连续运行 100 轮短 Loop；可见内容不回跳，实例和 DOM 数量在预设窗口上限附近稳定，回收时当前音符屏幕位置基本不变。

### H6：最终回归与交付

- 运行命令检查及新增测试，重新验证核心浏览器矩阵。
- 用实际生产入口验证加载、两布局、三练习模式、反复、Loop、暂停恢复和页面缓存恢复。独立测试 facade 不能替代生产烟测。
- 更新开发/测试文档和实际结果；注明硬件、听感、触摸、平台限制，区分本轮实际执行与历史记录。
- 记录最终文件清单、支持范围、性能测量和未解决问题。

| 隔离 | 默认 LED 与关闭 LED；生产 bundle 不含测试入口；原始谱保存和备份不含展开副本 |

关键断言：

1. 对每个谱例给出人工期望顺序，再比较实际原谱遍历和显示顺序。不能只拿同一个函数输出互相比较。
2. 正常自动演奏的逻辑显示 X 单调不减；第二次出现的 A 位于第一次 B 右侧。
3. Wait 等待时 eventId、待弹集合、显示目标保持不变；重绘也不推进它们。
4. 同一原谱音符不同 occurrence 的锚点不同；跨布局源音符身份保持一致。
5. 相同输入与受控时钟下，两种布局的判定结果和音频/MIDI事件一致，仅显示观察不同。
6. 自动跟随稳定后，非首尾边界的光标接近既定 33% 区域；过渡允许平滑追赶。记录实际窗口、速度、采样轨迹及误差，不能用任意瞬时阈值掩盖问题。
7. 块回收前后，在相同逻辑位置比较屏幕坐标，目标误差不超过 1 CSS px；真实设备上达不到时解释测量误差并处理可见跳动。
8. 空间占用受窗口策略约束，不能只有 DOM 有上限，而后台仍保存每一轮 OSMD 实例和无限映射。
