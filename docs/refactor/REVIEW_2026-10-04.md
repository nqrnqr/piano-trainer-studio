## 发现：P2 — 从浏览器前进/后退缓存恢复后，应用仍处于销毁状态

位置：`src/main.ts:4`。

```ts
window.addEventListener('pagehide', () => app.dispose(), {once: true});
```

该监听器不检查 `PageTransitionEvent.persisted`。当浏览器准备缓存当前页面以供前进/后退恢复时，也会发出 `pagehide`。缓存恢复会继续使用原来的页面与 JavaScript 状态，不会重新执行入口脚本。见 [MDN pagehide](https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event) 和 [浏览器往返缓存说明](https://web.dev/articles/bfcache)。

当前实现会产生以下结果：

- `app/services.ts:1001` 把 `disposed` 永久设为 `true`，随后销毁所有服务。
- `ui/display-controls.ts:147` 移除 Play/Reset 的点击处理器；其他控件的监听器也被移除。
- `ui/virtual-keyboard-controls.ts:112` 删除虚拟琴键，同时移除原有的 `pageshow` 音频恢复监听器。
- MIDI 监听、音频节点和乐谱加载服务均被清理。
- 没有生产入口负责在恢复时重建这些资源。直接再调用同一个实例的 `init()` 也无效，因为 `app/services.ts:946` 会在 `disposed` 为真时返回。

触发条件：离开应用页面，再通过前进/后退返回，且浏览器实际命中 bfcache。恢复后控件会失效，需要刷新页面。是否命中缓存取决于浏览器和页面所用 API；不是所有返回操作都会触发。

### 本次验证

用 esbuild 转换真实 `src/main.ts`，在 Node VM 中仅替换 bootstrap 为记录调用的对象，以 `EventTarget` 依次发送两个 `persisted=true` 的事件。结果为：

```text
pagehide(persisted=true) -> pageshow(persisted=true)
calls: ["init", "dispose"]
```

这是入口事件路径验证。尚未在真实浏览器中完成 bfcache 导航复现；上述控件影响由实际 dispose 实现确认。

### 修复建议

区分可恢复的页面挂起与最终销毁。对 `persisted=true` 保留应用的可恢复状态，并按需要暂停播放、释放音符；对真正离开页面执行最终清理。若选择销毁后重建，则必须明确恢复乐谱与用户状态，不能仅调用已销毁实例的 `init()`。

同时重新考虑 `{once: true}`：页面可能多次进入和离开缓存。补充多次挂起/恢复、Play/Reset、虚拟琴键、布局切换及 MIDI 重连测试。

### 为什么现有测试未覆盖

`docs/testing/module-test-frame.js` 把生产 bundle 替换为测试 bundle，后者由 `src/testing/main.ts` 启动。`testing/facade.ts` 直接创建服务，并提供显式 dispose/recreate，但没有执行生产 `src/main.ts` 的 pagehide 监听逻辑。应增加真实生产入口的生命周期测试；不必为此开放生产内部状态。
